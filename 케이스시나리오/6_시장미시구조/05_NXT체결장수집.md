# 시나리오 5. NXT 체결장(틱) 수집 — 프리·애프터 체결을 DB에 쌓기

## 한 줄 요약
넥스트레이드(NXT)에서 거래된 **모든 종목의 체결 하나하나(틱)** 를 매일 받아 DB에 쌓습니다.
NXT는 **08:00~20:00** 거래하므로, KRX가 열기 전(프리)과 닫은 뒤(애프터)의 체결이 그대로 들어옵니다.
[02_실시간호가적재](02_실시간호가적재.md)가 "호가창"을 쌓는다면, 이건 **"실제 체결"** 을 쌓습니다.

## 이게 답해주는 질문 / 왜 하나
- 어젯밤 **애프터장에서 오른 종목이 다음 날 KRX 시초가에서도 오르나?**
- **프리장(08:00~08:50) 체결이 그날 KRX 시가를 얼마나 예고**하는가
- 애프터·프리의 체결이 **매수세가 친 것인지 매도세가 친 것인지**, 스프레드는 얼마였는지
- 하루 중 NXT 거래가 **어느 시간대에 몰리는가**(정규장 vs 시간외)

> 핵심 동기: KRX 시초가는 하룻밤 사이 쌓인 정보가 한 번에 반영되는 순간입니다. 그 "하룻밤"에
> 실제로 무슨 거래가 있었는지는 **NXT 체결장에만 남아 있습니다.**

## 확인된 사실 (실측)

**① NXT는 하루 12시간 거래합니다.** 삼성전자 2026-05-08 실제 데이터:

| 세션 | 시간 | 체결 건수 | 비중 |
|---|---|---|---|
| 프리 | 08:00~08:50 | 545,149 | 24% |
| 메인 | 09:00~15:20 | 1,349,231 | 60% |
| 애프터 | 15:40~20:00 | 354,371 | 16% |

→ **프리+애프터가 전체 체결의 40%.** 표본 100종목 중 애프터 100%·프리 99%가 거래됐고,
거래량 기준으로는 중위 22%가 시간외에서 발생합니다. 시간외는 예외가 아니라 일상입니다.

**② 체결 시각은 초 단위입니다.** `F15019`는 `HHMMSSss` 형식(8000000 = 08:00:00.00)이지만
1/100초 자리는 **항상 00**입니다(1.8억 행 전수 + 전체 필드 실호출 확인 — API 원천 한계).
같은 초에 최대 6,764건이 몰리는데, 그 안의 순서는 `F16604`(종목별저장일련번호)로 구분합니다.

**③ 보관 기간이 약 101일뿐입니다.** 2026-07-13 기준 2026-04-03은 조회되고 04-02는 실패했습니다.
→ **틱은 매일 하루치씩 영구 소실되는 소멸성 자원**입니다. 지나간 건 되찾을 수 없습니다.

## LLM에게 이렇게 말하세요
- "NXT 체결 데이터 오늘치 수집해줘"
- "NXT 틱 수집 진행 상황 알려줘"
- "삼성전자 어제 프리장 체결 100건만 보여줘"
- "애프터장 거래가 많았던 종목 뽑아줘"

## 무엇이 만들어지나
1. **DB 스키마** (`nxt_krx_schema.sql`) — 체결 테이블 `nxt_tick`(월 단위 파티션·압축),
   드라이버 `nxt_universe`, 진척 기록 `ingest_log`, 세션 구분 뷰 `nxt_tick_session`
2. **수집기** (`nxt_krx_ingest.py`) — 매일 신규 거래일을 자동 편입하고 한도까지 수집
3. **일일 자동 실행** (`run_daily.bat`) — 작업 스케줄러 등록용(21:00, NXT 장 마감 후)

## 이렇게 돌립니다

```bash
# 매일 이것 하나면 됩니다 (신규 거래일 편입 → 체결 수집)
python nxt_krx_ingest.py --daily

# 진행 상황 확인
python nxt_krx_ingest.py --plan
```

무인 실행은 작업 스케줄러에 `run_daily.bat`을 21:00로 걸어둡니다. 한도(1GB)에 닿으면 스스로
멈추고, 다음 날 **받다 만 지점부터** 이어서 진행합니다.

### 왜 이 9개인가

**받는 것 (9개)** — 체결을 재구성하는 데 꼭 필요한 것들입니다.

| 저장 컬럼 | 쓰임 |
|---|---|
| `ts`(F15019) · `price`(F15001) · `qty`(F15020) | 체결 그 자체 — 언제·얼마에·몇 주 |
| `seq`(F16604) | 같은 초에 몰린 체결의 순서 |
| `side`(F15022) | 매수 주도(B/BB) / 매도 주도(S/SS) / 대량·바스켓 구분 |
| `ask1`·`bid1`(F14501/F14531) | 체결 시점 최우선 호가 → **매도호가를 쳤나 매수호가를 쳤나**, 유효 스프레드 |
| `ask_qty1`·`bid_qty1`(F14511/F14541) | 그 시점 호가 잔량 → 호가 불균형 |

**안 받는 것 (29개)** — 세 부류로 나뉩니다.

1. **계산으로 대체 가능** (`F15472` 대비, `F15004` 등락율, `F15015` 누적거래량, `F15023` 거래대금,
   `F15028` 시가총액). 예: 거래대금 = 체결가 × 체결량, 누적거래량 = 체결량 누적합.
   `F15028`은 13자리 숫자가 매 틱 반복돼 **혼자 응답을 30% 키우는데**, 체결가 × 상장주식수라
   틱 하나만 있으면 나머지는 역산됩니다.
2. **동시호가·예상체결 전용 14개** (`F15176`~`F15326`, `F30612`~`F30618`). 장 시작·마감의
   동시호가 구간에서만 의미가 있고, 접속매매 중엔 중복값이거나 비어 있습니다.
3. **명세 밖 2개** (`F11505` 값 없음, `F12506` 조회일자와 동일).

### 필드를 더 받고 싶다면 — 만료 레이스를 먼저 보세요

필드를 늘리면 응답이 커지고, 하루 1GB 한도로 받을 수 있는 거래일 수가 줄어듭니다.
보관창은 **매일 0.71거래일씩** 밀리므로, 수집 속도가 이보다 느려지면 **미수집 구간이
손에 닿기 전에 영구 소멸**합니다.

| 구성 | 응답 배수 | 수집 속도 | 만료 속도 | 순증 | 판정 |
|---|---|---|---|---|---|
| 5필드(호가 없음) | ×1.00 | 1.55일/일 | 0.71일/일 | +0.84 | 안전 |
| **9필드(현재)** | **×1.77** | **0.88일/일** | 0.71일/일 | **+0.16** | 채택 |
| 10필드(+시가총액) | ×2.07 | 0.75일/일 | 0.71일/일 | +0.04 | 사실상 무승부 |
| 38필드(전체) | ×7.41 | 0.21일/일 | 0.71일/일 | **−0.51** | **불가** |

38필드는 완주에 212일이 걸리는데 보관창은 101일이라 **애초에 불가능**합니다.

## 결과 읽는 법

수집된 체결은 세션 구분 뷰로 바로 나눠 볼 수 있습니다.

```sql
USE nxt_krx;

-- 한 종목·하루의 체결 (시각·세션·호가 포함)
SELECT
  CONCAT(LPAD(ts DIV 1000000,2,'0'), ':',
         LPAD(MOD(ts DIV 10000,100),2,'0'), ':',
         LPAD(MOD(ts DIV 100,100),2,'0'))        AS 시각,
  CASE WHEN ts <  9000000 THEN 'PRE'
       WHEN ts < 15300000 THEN 'MAIN'
       ELSE                    'AFTER' END       AS 세션,
  price AS 체결가, qty AS 체결량,
  bid1  AS 매수호가, ask1 AS 매도호가,
  CASE WHEN price >= ask1 THEN '매도호가 침(매수주도)'
       WHEN price <= bid1 THEN '매수호가 침(매도주도)'
       ELSE '중간' END                            AS 체결방향
FROM nxt_tick
WHERE code = '005930' AND trade_date = '2026-05-08'
ORDER BY n
LIMIT 100;

-- 세션별 집계
SELECT session, COUNT(*) 체결수, SUM(qty) 거래량
FROM nxt_tick_session
WHERE code = '005930' AND trade_date = '2026-05-08'
GROUP BY session;
```

- **`ORDER BY n`이 체결 순서입니다.** `ts`는 초 단위라 같은 초에 수백 건이 몰리는데,
  그 안의 순서는 `n`(= `seq` 순서)으로만 구분됩니다. `ORDER BY ts`로 정렬하면 섞입니다.
- **체결방향**: 체결가가 매도호가 이상이면 매수 주도, 매수호가 이하면 매도 주도입니다.
  `side`(F15022)와 교차 검증할 수 있습니다.

## 거래량 검증 — 무엇을 빼야 진짜 거래량인가

체결장을 그대로 `SUM(qty)` 하면 **공식 거래량보다 큽니다.** `chg_type`(F30614)이 `69`인 행은
기세(호가만 움직인 것)라 실제 체결이 아니고, 거래소 집계에서 빠지기 때문입니다.

정답지는 넥스트레이드 공식 통계입니다. `nxt_daily` 표에 담아 두었습니다
(`nxt_daily_load.py`, 출처 `nxt-data-api`). **CHECK API 한도를 쓰지 않습니다.**

```sql
-- 한 거래일의 (종목별) 대조: 차이가 0이어야 정상
SELECT t.code, d.qty AS 공식거래량,
       SUM(CASE WHEN t.chg_type <> 69 THEN t.qty END) AS 틱거래량,
       SUM(CASE WHEN t.chg_type <> 69 THEN t.qty END) - d.qty AS 차이
FROM nxt_tick t JOIN nxt_daily d
  ON d.trade_date = t.trade_date AND d.code = t.code
WHERE t.trade_date = '2026-06-08' AND t.src IS NULL
GROUP BY t.code, d.qty
HAVING SUM(t.chg_type IS NULL) = 0;      -- chg_type 이 완비된 종목만
```

주의할 점 두 가지입니다.

- **공식 거래량은 두 세션의 합**입니다. `regular_market`(정규시장) + `closing_price`(종가매매).
  종가매매를 빼먹으면 소액 잔차가 남습니다(실측: 066570 315주, 454910 29주).
  `nxt_daily.qty`는 이미 둘을 더한 값입니다.
- **`side`(F15022)로는 69를 못 가려냅니다.** `side=3`은 69를 포함하는 더 넓은 집합이라
  종목·날짜마다 6~12건이 어긋납니다. 시간대(15:19:59~15:39:59) 규칙도 실패했습니다
  (400표본 중 48건, 12%만 일치). **`F30614`을 실제로 받는 것 외에 대안이 없습니다.**

`chg_type`이 NULL인 과거 수집분은 어느 행이 69인지 특정할 수 없지만, **수량은 알 수 있습니다**:
`69 거래량 = 틱 SUM(qty) - nxt_daily.qty`. 총량 분석은 이걸로 보정하면 됩니다.

## 주의사항

- **틱은 소멸성입니다.** 보관 101일이 지나면 되찾을 수 없습니다. 수집을 며칠 쉬면 그만큼
  영구히 사라집니다. 하루라도 빠뜨리지 않는 게 이 파이프라인의 제1원칙입니다.
- **초 이하 해상도는 없습니다.** 같은 초 안의 밀리초 간격은 API가 주지 않습니다.
  HFT 마이크로구조 분석은 이 데이터로 불가능합니다.
- **상폐 종목은 장중 데이터가 조회되지 않습니다**(일봉만 남음). 소폭의 생존편향이 있습니다.
- **호가 4개는 2026-07-28 이후 수집분부터** 있습니다. 그 이전 데이터는 `ask1` 등이 NULL입니다.
- **일 한도 1GB는 `cust_id` 단위**입니다. 수집이 한도를 다 쓰면 같은 날 다른 조회가 막힙니다.
  한도 초과는 HTTP 200 + `success:false`로 오므로, 빈 결과로 흘리면 "거래 0건"으로 조용히
  기록됩니다(수집기는 예외로 올려 중단합니다).
- **등록 IP PC에서만** 실데이터가 들어옵니다.
