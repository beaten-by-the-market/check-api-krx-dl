제목: [CHECK API 문의] 502로 실패한 요청이 일 사용량에 계산되는 것으로 보입니다 (tick_date 대용량 응답)


안녕하십니까.

CHECK API로 체결 데이터를 수집하던 중, 응답을 한 바이트도 받지 못한 요청이
일 사용량 한도에 계산되는 것으로 보이는 현상이 있어 문의드립니다.

수치가 정확히 맞아떨어져 확신을 갖고 문의드리며, 확인 부탁드립니다.


1. 현상 요약

   대용량 응답이 예상되는 요청에서 HTTP 502(Proxy Error)가 반복 발생했습니다.
   당사는 응답을 전혀 수신하지 못했으나, 그 시도들이 일 사용량에는 반영된 것으로
   계산됩니다.


2. 문제가 된 요청

   POST https://checkapi.koscom.co.kr/stock/m222/tick_date

   cust_id   = (당사 고객번호)
   auth_key  = (당사 인증키)
   jcode     = 005930
   edate     = 20260506
   data_list = F16604,F14501,F14531,F14511,F14541

   결과: HTTP 502 Proxy Error
   재시도: 2초, 4초, 8초, 16초, 32초, 60초 간격으로 총 7회 시도, 전부 동일하게 502
   수신 데이터: 0 바이트 (7회 모두)


3. 사용량 계산이 맞지 않는 근거

   2026년 8월 3일 당사 수집 기록입니다.

   가. 당사가 실제 수신한 양

       548건 호출, 합계 461 MB
       (응답 본문 바이트를 호출 단위로 누적한 값입니다)

   나. 그런데 API는 한도 초과를 반환

       461 MB 시점에 아래 응답을 받았고, 이후 모든 요청이 동일하게 거부되었습니다.

       {"success": false,
        "message": "일 최대 사용량 1,000,000,000Bytes를 초과했습니다."}

   다. 차이 539 MB 가 502 재시도분과 일치

       위 2번 요청(005930 / 20260506)의 예상 응답 크기를 같은 날 같은 endpoint의
       성공 응답으로 추정하면 다음과 같습니다.

           종목      체결 건수    수신 크기    건당
           000660     387,342건    35.1 MB     91 바이트
           034020     195,940건    17.4 MB     89 바이트
           005380     123,096건    10.9 MB     89 바이트

       005930의 2026년 5월 6일 체결 건수는 854,332건입니다.
       건당 90 바이트로 계산하면 예상 응답 크기는 약 77 MB입니다.

           77 MB × 7회 시도 = 539 MB
           461 MB(수신) + 539 MB(미수신) = 1,000 MB

       한도 초과 시점과 정확히 일치합니다.


4. 문의 사항

   가. 502 등으로 전송이 실패한 요청도 일 사용량에 계산되는 것이 맞는지
       확인 부탁드립니다.

   나. 맞다면, 이용 기관 입장에서는 수신하지 못한 데이터에 대해 한도를 소모하게
       됩니다. 전송이 완료되지 않은 요청은 사용량에서 제외하는 것이 합리적이라고
       생각되어 검토를 요청드립니다.

   다. 502의 원인이 응답 크기 제한이라면 그 임계값을 알려주시면 감사하겠습니다.
       임계값을 알면 사전에 요청을 나누거나 필드를 줄여 회피할 수 있습니다.

   라. 대용량 (종목, 일자) 조합을 안정적으로 받는 방법이 있는지 문의드립니다.
       tick_date에는 조회 범위를 나누는 파라미터(시간대, 건수, 페이지 등)가
       없는 것으로 확인됩니다. 분할 조회 수단이 있다면 안내 부탁드립니다.


5. 참고 사항

   - 같은 종목·일자를 전체 필드(data_list 미지정)가 아닌 9개 필드로 요청했을 때는
     2026년 7월 28일에 정상 수신된 이력이 있습니다(854,332건). 항상 실패하는 것은
     아니며, 시점이나 서버 부하에 따라 달라지는 것으로 보입니다.
   - 등록 IP 환경에서 POST 방식(form-urlencoded)으로 호출하고 있습니다.
   - 초당 1건 이하로 순차 호출하며, 조회 제한 관련 메시지는 수신되지 않았습니다.
   - 당사는 재시도 로직을 1회로 축소하여 동일한 소모가 재발하지 않도록 조치했습니다.
